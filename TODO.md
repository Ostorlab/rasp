## Runtime: all platforms

- **`run_plugins` also gives the plugins the observations.** Running the plugins' checks and handing out the observations are one function today, so the plugins' `on_observations` is called from `run_plugins`. The runtime should have its own `on_observations` step, and call the plugins' `on_observations` after its own built-in handling.
- **The Android and iOS monitoring code is duplicated.** Both `monitoring.cpp` files start the thread, run the checks and the plugins at random intervals and log the observations, with the same code. The monitoring should be one shared implementation, and each platform should only provide its built-in checks.

## Runtime: iOS

- **The sandbox probe likely misses iOS 15 and later.** `jb.sandbox_escape` creates `/private/.rasp_sandbox_probe`. Since iOS 15 the system volume is sealed and read-only, and `/private` is on it, so the write is likely refused with `EROFS` whether or not the sandbox is in force, and the probe reports `false` on jailbroken devices too. To confirm on a jailbroken device.
- **The exception-port probe can be lied to.** `dbg.exception_ports` asks for the ports through the `task_get_exception_ports` function of `libsystem_kernel`. A hook on that function can report no ports while a debugger has set them. Sending the same request as a Mach message through the `mach_msg` trap directly, as a second source, would make a hook on the library function show as two values that disagree.
- **The tunnel probe misses IPv6-only VPNs and may report a stock `ipsec` interface.** `mitm.tunnels` reports a `utun`, `ipsec`, `ppp`, `tun` or `tap` interface only when it is up and carries an IPv4 address, because stock iOS keeps several `utun` interfaces open for its own services. The kernel gives a `utun` no address of its own: the VPN app assigns them, and WireGuard's iOS app, for one, assigns only the addresses its configuration lists, so a configuration with only IPv6 addresses opens a tunnel the probe never reports. The other way round, Wi-Fi calling likely runs over an `ipsec` interface whose inner address the carrier assigns, which can be IPv4, so a stock device on Wi-Fi calling may report it. To confirm on stock devices, with Private Relay, Wi-Fi calling and a personal hotspot on, which interfaces carry which addresses. Telling a VPN's tunnel apart without the address family needs another source, such as the `__SCOPED__` keys of `CFNetworkCopySystemProxySettings`, which list the interfaces that have a VPN or proxy configuration.
- **A proxy found by Wi-Fi auto-discovery is likely missed.** In the Wi-Fi settings, Configure Proxy set to Automatic with no URL makes the device find its proxy through WPAD. `mitm.proxies` reads the auto-config URL and its enable flag, but the key that marks auto-discovery, `kCFNetworkProxiesProxyAutoDiscoveryEnable`, is marked unavailable on iOS in the SDK, so the probe likely reports an empty list. To confirm on a device whether the settings carry the key anyway, under its literal name `ProxyAutoDiscoveryEnable`.
- **The proxy probe has a single source.** `mitm.proxies` reads `CFNetworkCopySystemProxySettings` only, a function bypass scripts commonly hook. A hook that returns empty settings hides the proxy. A second source would make the hook show as two values that disagree. To try on a jailbroken device with Frida first.
- **The user CAs are not seen, and interception through them is not caught yet.** iOS has no public API that lists user-installed certificate authorities, so `mitm.user_cas` is unsupported. A user-installed root only matters when a proxy uses it to re-sign the app's TLS traffic, and that can be caught: the runtime opens a TLS connection to a server whose public key it knows, and reports whether the key the system accepted is the expected one.
- **The packer accepts apps below the runtime's minimum iOS version.** The runtime supports iOS 12.0 and later, and the packer packs apps that declare an older minimum. On those older devices the runtime would fail to load.

## Runtime: Android

- **The payload keys are derivable from the app alone, so full-emulation dumping has a ceiling, not a wall.** A blind attacker who executes the library in a whole-app emulator (unidbg-class) needs no key and no understanding: the bootstrap runs as DT_INIT, the gates fold poison into the key instead of aborting (so a hooked exit reveals and bypasses nothing), and the Java arm now demands that the emulator resolve the app's program steps — real class loading, real hierarchies — correctly enough to derive the armed master, silently failing when it does not. But a carefully configured emulation still runs the whole chain and dumps the decrypted dexes at `InMemoryDexClassLoader`, because every key input is, in the end, app-derivable. Deepening the program's steps needs a dex reader on the packer side (fields, methods and per-app hierarchies of the app's own clear classes, which a fake loader must answer from the real dex). Only key material that an emulator cannot reproduce — the Android Keystore, a TEE-held secret, or a server-enrolled share with attestation — turns the ceiling into a wall. That needs an enrollment or first-run flow, not just the packer.
- **The `/data/adb` paths are never reported.** `root.fs_paths` looks for the Magisk, KernelSU and APatch folders under `/data/adb`. That folder is `drwx------ root`, so `access` and `stat` fail with permission denied on rooted and stock devices alike, and those paths are never reported. Seen on an Android 14 emulator rooted with Magisk v30.7: `/data/adb/magisk`, `magisk.db` and `modules` exist, and the adb shell user can't reach them; an app has fewer rights still. They stay in the list for devices where a root tool loosened the folder's permissions.
- **The SELinux probe may report an error on every device, and misses modern root.** Recent Android versions may forbid apps to read `/sys/fs/selinux/enforce`, and `root.selinux_enforcing` then reports an error on every device. The adb shell user could read it on Android 14 and 17 emulators; whether an app can is not yet confirmed. Even when it can be read, Magisk, KernelSU and APatch keep SELinux enforcing, so the probe only catches older ways of rooting and permissive custom ROMs.
- **Root hiding defeats these checks.** Magisk's DenyList and Shamiko unmount the root tool's files and mounts for the app, and `resetprop` changes the build properties. The checks catch a device that doesn't hide its root. Catching one that does needs probes the hiding doesn't cover, such as the app's own memory map and threads.
- **Installed root apps aren't checked.** An installed root manager, an app that needs root, or a root-hiding app is a strong signal. RootBeer, an open-source Android root-detection library, lists their package names in its `Const.java`, and KernelSU (`me.weishu.kernelsu`) and HideMyApplist (`com.tsng.hidemyapplist`) belong on that list too. Looking them up needs `PackageManager` through JNI. Since Android 11, an app only sees the packages its manifest declares in `<queries>`, so the packer would have to add them. Magisk can also reinstall its app under a random package name.

## Packer: Android

- **A synthetic class R8 placed outside the app's packages ships in the clear.** With an R8 mapping, the packer protects every obfuscated package that holds a class whose original name is under the app's package. A class R8 synthesised with no mapping line that landed in a package holding none of the app's classes is not protected. This is the conservative choice: it never splits a Java package across class loaders, so it never breaks package-private access, but a little of the app's generated code can stay readable. A way to attribute such classes to the app would close the gap.
- **The no-mapping repackage warning is a guess.** Without a mapping, the packer warns when few of the app's classes are under its package, which is the shape of an R8-repackaged build. A library-heavy app that was not repackaged can trip the same warning, and a lightly repackaged one can slip under it. The reliable signal is the mapping itself; the warning only nudges the operator to pass it.
- **The self-decrypt bootstrap is the same in every app of one build.** The shovel (gen_kdf_shovel.py) compiles the derivation once per ABI and build, so the bootstrap's machine code is byte-identical across every app packed from the same release: an attacker who reverses it once amortizes the effort over all of them. Generating per-app variants at pack time, the way the fold invents a per-app recipe, would raise that cost. The bootstrap's post-decrypt digest check and the fold's sensor guard still hold either way.
- **A loaded business dex lives on in ART's memory.** The runtime's `key_schedule` keeps no root key in the app, the loader wipes its own copy of a decrypted dex, and every decryption now re-observes the process through the sensor guard (a tracer or a patched library silently breaks the next decryption), but `InMemoryDexClassLoader` still keeps the copy it defines classes from, so a dumper running on the device can read a business dex between its load and the process's end. Shrinking that window needs method-level decryption: only the body of a method decrypts when it is first invoked, which means intercepting ART's resolution of it.
- **The fold program's interpreter is readable in the binary.** No key ships in the app, and each app's fold is a different random recipe of real inputs and decoys, but the interpreter that runs the recipe is fixed code in `librasp.so`: an attacker who fully reverses it once can parse any app's program, because the program is data. White-boxing the derivation would raise that cost further.
- **The shipped library's section headers map its protection.** Every section keeps its name, address and size. The renamed sections still stand out: `.text.hot` is the only executable section left in the clear, aligned unlike real hot code, and it holds the self-decrypt bootstrap; `.init` is writable data, where `.init` is normally code, and it holds the runtime's config; `.data.rel` holds the bootstrap's metadata. The table also gives the exact bounds of every encrypted section, so a reader knows where the bootstrap is and what it decrypts before reading any code.
- **The runtime's config ships readable.** The config section is not encrypted. It shows the build id, the enabled checks and the per-app name of the stub class, so the class the packer renames to hide the entry point is named in the library.
- **The shipped library names the exact toolchain.** `.comment` holds the clang and LLD versions and their build numbers, and `.note.android.ident` the NDK version and the API level. The runtime doesn't need either to load; they only tell a reader how it was built.
- **One build id marks every protected app.** `.note.gnu.build-id` is the same in every app packed from one runtime release, so a single hash finds all the apps that ship it, in a store or in a malware database.
- **The dynamic section points at the bootstrap.** `DT_INIT` holds the address of the self-decrypt entry, in the clear code, so the ELF headers give the place to start reading.
- **`.data.rel.ro` ships in the clear.** `ENCRYPT_SECTIONS` lists it, but the packer leaves the whole `PT_GNU_RELRO` range unencrypted, and `.data.rel.ro` lies inside it. It holds the pointers the dynamic linker fills in, thousands of them into `.text`, which show where the runtime's function tables point.
- **The import table lists what the runtime checks.** The runtime imports libc functions by name, among them `getifaddrs`, the system-property functions, `opendir` and `readdir`, `access` and `stat`, `dl_iterate_phdr` and `mlock`. The encryption hides the code, but the names say what it looks at.
- **The stub dex is patched in place, not built for each app.** The packer takes the prebuilt `stub.dex` and overwrites its class, source file and library names with random strings of the same byte length, each drawn to sort between the same neighbours in the dex's string table. Every protected app carries a stub whose names keep the same lengths and table positions, a fingerprint the renaming exists to remove, and a change to the stub's strings can break the patch. The stub should be written as a fresh dex at pack time, with names of any length and value.
- **The packer doesn't see the library's relocations.** `self_encrypt.py` recognises `SHT_RELR` (19), but the NDK linker writes the relative relocations to an `SHT_ANDROID_RELR` section (0x6fffff00), so the packer knows none of them when it chooses what to encrypt. None lands in an encrypted region today, but one that did would be corrupted at load: the dynamic linker would add the load bias to encrypted bytes. The packer's tests build their libraries with `SHT_RELR`, so they don't catch it.
